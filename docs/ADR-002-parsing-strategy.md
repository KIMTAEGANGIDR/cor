# ADR-002: 파싱 전략 결정

> **상태**: 초안 (실제 데이터 확인 후 확정 필요)
> **날짜**: 2025-01-21
> **결정자**: 프로젝트 담당자

## 컨텍스트

OCR로 추출한 텍스트를 구조화된 법령 데이터로 변환하는 파싱 전략이 필요함.

### 최종 목표

**100%에 근접하는 정확도 + 국제 규격 XML (Akoma Ntoso) 변환**

- 조문 단위 정확한 파싱 (BAB/Pasal/Ayat/Huruf/Angka)
- Akoma Ntoso 3.0 XML 표준 준수
- 휴먼 검토 프로세스를 통한 품질 보장
- 법적 인용 가능한 수준의 정확도

## 결정

### 1. 파싱 파이프라인 (자동 + LLM 검증 + 휴먼)

```
[Raw OCR Text]
      ↓
Phase 1: 전처리 (노이즈 제거)
      ↓
Phase 2: 구조 추출 (연도별 파서)
      ↓
Phase 3: LLM 자동 검증 (기계적 + 의미론적)
      ↓
  ┌───┴───┐
  │       │
 Pass    Flag
  ↓       ↓
샘플링   휴먼 검토
(대학원생) (대학생→대학원생→변호사)
  │       │
  └───┬───┘
      ↓
Phase 4: Akoma Ntoso XML 변환
      ↓
[최종 산출물] → 100% 정확한 XML
```

### 2. 전처리가 핵심

노이즈 제거가 잘 되면 파싱은 상대적으로 쉬워짐:

- 워터마크 제거 (`www.djpp.depkumham.go.id` 등)
- 페이지 헤더/푸터 제거 (`PRESIDEN REPUBLIK INDONESIA`)
- OCR 오류 수정 (`2OO9` → `2009`, `Pasa1` → `Pasal`)
- 줄바꿈 정규화 (단어 중간 줄바꿈 병합)

### 3. 연도별 파서 분리

인도네시아 법령은 연도별로 포맷이 다름:

| 연도 | 특징 | 우선순위 |
|------|------|----------|
| 2020+ | 비교적 일관, SK No 포함 | **1순위** |
| 2000-2019 | 스캔+OCR, 페이지 헤더 혼입 | 2순위 |
| 1970-1999 | 과도기, "Menetapkan:" 등장 | 3순위 |
| ~1969 | 네덜란드어 혼용, 불규칙 | 4순위 (휴먼 비중 높음) |

**모든 연도 대상** - 레거시 문서도 스킵하지 않음

### 4. LLM 기반 검증 시스템

#### 왜 LLM인가?

기존 접근법의 문제:
```
사람 A가 검수 → "문제 없음" → 통과
                    ↓
             실제로는 오류 있음
                    ↓
             영원히 묻힘
```

**사람이 못 찾으면 아무도 못 찾는 구조** → 100% 정확도 불가능

#### LLM 검증 (전수 검사)

```
[OCR 텍스트] + [파싱 결과]
         ↓
┌────────────────────────────────┐
│      LLM 자동 검증              │
│                                │
│  1. 기계적 비교                 │
│     - 글자/단어 수 일치         │
│     - 누락 텍스트 검출          │
│     - Pasal 번호 연속성         │
│     - 구조 완전성               │
│                                │
│  2. 의미론적 비교               │
│     - "파싱이 원본을 반영하나?" │
│     - 문맥상 이상한 부분        │
│     - 잘린 문장, 뒤섞인 순서    │
│     - 참조 관계 정합성          │
└────────────────────────────────┘
         ↓
    Pass / Flag
```

#### 장점

| 기존 (사람 중심) | 개선 (LLM + 사람) |
|------------------|-------------------|
| 사람 2명이 전수 검사 | LLM이 전수 검사 |
| 사람이 놓치면 끝 | LLM이 1차 필터 |
| 비용 높음 | 사람은 플래그된 것만 |
| 일관성 낮음 | LLM은 일관적 |

#### LLM 검증 파이프라인 상세

```
[파싱 결과 DB]
      ↓
┌─────────────────────────────────────┐
│ Step 1: 배치 준비                    │
│    - 문서 청킹 (컨텍스트 제한 고려)   │
│    - 우선순위 정렬 (연도, 중요도)     │
│    - 비용 예측 및 예산 확인           │
└─────────────────────────────────────┘
      ↓
┌─────────────────────────────────────┐
│ Step 2: 기계적 비교 (코드, LLM 불필요)│
│    - 글자 수 / 단어 수 일치          │
│    - Pasal 번호 연속성               │
│    - 구조 완전성 (열린 괄호 등)       │
│    → 여기서 실패 시 바로 Flag        │
└─────────────────────────────────────┘
      ↓
┌─────────────────────────────────────┐
│ Step 3: LLM 의미론적 비교 (1차)      │
│    - 모델: Haiku / GPT-4o-mini      │
│    - 배치 API 호출 (Rate limit 고려) │
│    - 응답: Pass / Flag / Uncertain   │
└─────────────────────────────────────┘
      ↓ (Uncertain만)
┌─────────────────────────────────────┐
│ Step 4: LLM 의미론적 비교 (2차)      │
│    - 모델: Sonnet / GPT-4o          │
│    - 더 정밀한 검증                  │
│    - 여전히 불확실 → 휴먼 리뷰       │
└─────────────────────────────────────┘
      ↓
┌─────────────────────────────────────┐
│ Step 5: 결과 저장                    │
│    - 검증 결과 DB                    │
│    - Flag 사유 기록                  │
│    - 비용 추적                       │
└─────────────────────────────────────┘
      ↓
[휴먼 리뷰 큐] / [Pass 문서 풀]
```

#### 모델 선택 전략

| 단계 | 모델 | 비용 | 용도 |
|------|------|------|------|
| 1차 의미론적 | Haiku / GPT-4o-mini | 저렴 | 대부분 여기서 Pass |
| 2차 의미론적 | Sonnet / GPT-4o | 중간 | Uncertain만 재검증 |

**비용 추정** (2만 건, 평균 10페이지 기준):
- 전부 고급 모델: ~$600-800
- 하이브리드 (90% 저렴 + 10% 고급): ~$80-120

#### 청킹 전략 (긴 문서 처리)

일부 법령은 500페이지 이상 → 한 번에 LLM에 넣으면:
- 1M 토큰 (컨텍스트 초과)
- 한 문서에 $3-15 비용
- 비효율적

**해결: Pasal 단위 청킹**

```
500페이지 법령
     ↓
Pasal 단위로 분할
     ↓
각 Pasal별로 검증 (2-5K 토큰)
     ↓
결과 합산
```

| 전체 문서 | Pasal 단위 |
|----------|-----------|
| 1M 토큰/문서 | ~2-5K 토큰/Pasal |
| 컨텍스트 초과 | 모든 모델 가능 |
| 에러 시 전체 재시도 | 해당 Pasal만 재시도 |

#### LLM의 진짜 역할

단순 Pass/Flag가 아님. LLM이 해야 할 일:

```
1. 구조 검증
   - Pasal 개수, 번호 연속성

2. 의미 검증
   - 원본 의미가 파싱에 반영됐나?
   - 잘린 문장, 누락된 내용 없나?

3. 인간 판단 필요 케이스 식별
   - "이 부분은 A 또는 B로 해석 가능"
   - "여기는 원본 자체가 애매함"
   - "OCR 오류인지 원본인지 불명확"

4. 구체적 질문 생성
   - "Pasal 3 ayat (2)가 여기서 끝나는 게 맞나요?"
   - "이 단어가 X인지 Y인지 확인 필요합니다"
```

#### LLM 출력 형식 (상세)

```json
{
  "verdict": "PASS" | "FLAG" | "HUMAN_REQUIRED",
  "confidence": 0.85,

  "structure_check": {
    "passed": true,
    "issues": []
  },

  "semantic_check": {
    "passed": false,
    "issues": ["Pasal 5 ayat (3) 끝부분이 잘린 것 같음"]
  },

  "human_decisions_needed": [
    {
      "location": "Pasal 12 ayat (1)",
      "question": "이 문장이 여기서 끝나는 게 맞나요?",
      "options": ["여기서 끝남", "다음으로 이어짐"],
      "context": "원본 PDF 페이지 경계에서 발생"
    },
    {
      "location": "Pasal 15",
      "question": "'Penghasilan' vs 'Penghsilan' - OCR 오류인가요?",
      "options": ["Penghasilan이 맞음", "원본도 오타임"],
      "context": "OCR 신뢰도 낮은 구간"
    }
  ]
}
```

### 5. 휴먼 검토 프로세스 (3단계 피라미드)

```
LLM Flag → L1: 대학생 (다수)
              - OCR 오류 수정
              - 기본 구조 확인
              - 불확실 → L2로 에스컬레이션
                    ↓
           L2: 대학원생 (중간)
              - 복잡한 구조 파싱
              - L1 작업 샘플링 검증
              - 법적 해석 필요 → L3로
                    ↓
           L3: 변호사 (소수)
              - 법적 해석 최종 판단
              - L2 작업 샘플링 검증
              - 규칙 예외 결정
```

**LLM Pass 문서**: 대학원생이 샘플링 검증 (LLM 신뢰도 모니터링)

### 6. 품질 목표

| 단계 | 목표 |
|------|------|
| 자동 파싱 | 구조 추출 완료 |
| LLM 검증 | 전수 검사, Pass/Flag 분류 |
| 휴먼 리뷰 | Flag 문서 100% 검토 |
| 샘플링 검증 | Pass 문서 신뢰도 확인 |
| 최종 XML | Akoma Ntoso 3.0 **100% 정확** |

## 부록: 로컬 SLM 파인튜닝 옵션 검토

### API vs 로컬 SLM 비교

| | API (Haiku 등) | 로컬 SLM (파인튜닝) |
|---|---|---|
| **초기 비용** | 없음 | GPU 서버 + 개발 시간 |
| **운영 비용** | 토큰당 과금 | 전기세만 |
| **32,000건 이후** | 계속 과금 | 무료 |
| **프라이버시** | 데이터 외부 전송 | 로컬 유지 |

### 로컬 SLM 후보

| 모델 | 인도네시아어 | 추천도 |
|------|------------|-------|
| Qwen 2.5 (14B) | 좋음 (아시아어 강점) | ⭐⭐⭐ |
| SEA-LION | 좋음 (동남아 특화) | ⭐⭐⭐ |
| EXAONE | ? (한국어 특화) | ⭐⭐ |
| Llama 3 | 보통 | ⭐⭐ |

### 단계적 접근 (권장)

```
Phase 1: API로 시작
├─ Haiku/GPT-4o-mini로 첫 검증
├─ 인간 리뷰어가 수정
└─ → 학습 데이터 축적

Phase 2: 파인튜닝
├─ 축적된 데이터로 SLM 학습
├─ 소규모 테스트
└─ 성능 비교

Phase 3: 전환 (조건부)
├─ SLM이 충분하면 → 로컬로 전환
├─ 부족하면 → 하이브리드 유지
└─ 운영 비용 대폭 절감
```

### ⚠️ 로컬 SLM의 근본적 문제점

#### 1. 성능 천장

```
GPT-4o / Claude Sonnet: 100점 기준
├─ 70B 모델: ~80점
├─ 14B 모델: ~65점
└─ 7B 모델: ~50점

파인튜닝해도 천장이 있음
```

#### 2. 환각 (Hallucination)

소형 모델일수록 환각 심함:

```
검증 도구가: "네, 맞습니다" (실제론 틀림)
     ↓
오히려 오류를 통과시킴
     ↓
100% 정확도 목표와 정면충돌
```

**검증 도구가 오류를 만드는 최악의 상황 가능**

#### 3. "애매한 케이스" 판단 능력 부족

```
GPT-4o: "이건 A일 수도 있고 B일 수도 있어서
        인간이 확인해야 합니다"

7B 모델: "A입니다" (확신에 찬 오답)
```

**"모르겠다"고 말할 줄 아는 게 더 어려움**

#### 4. 인도네시아어 + 법률 도메인 조합

```
인도네시아어 데이터: 적음
법률 도메인 데이터: 적음
인도네시아어 법률: 매우 적음
     ↓
파인튜닝해도 기반이 약함
```

### 결론: 100% 정확도와 SLM

| 목표 | 적합한 도구 |
|------|------------|
| 80% 정확도 OK | SLM 가능 |
| **100% 정확도** | **대형 모델(API) 권장** |

> **100% 정확도 목표라면 SLM은 리스크가 높다.**
> 장기적으로 SLM 전환을 고려하되, 초기에는 API로 시작하고
> 충분한 학습 데이터 확보 후 성능 검증을 거쳐 전환 여부 결정.
